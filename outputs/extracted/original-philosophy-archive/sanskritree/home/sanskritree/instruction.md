Resources we didn't mention:
Sanskrit Sembank — Oliver Hellwig's DCS now has a semantic annotation layer: every word in the corpus linked to WordNet synsets in context. This is huge. It means you can query "all occurrences of citi across all texts with their disambiguated sense" and get that programmatically. GitHub: OliverHellwig/sanskrit/tree/master/dcs/data/conllu. This is the closest thing to pre-labelled semantic data for philosophical Sanskrit that exists.
Vedic Treebank (VTB) — 3,700+ sentences in Universal Dependencies CoNLL-U format, covering 600 years of Vedic texts. Hellwig et al. 2020. Gold-standard syntactic annotation. Directly usable for training parsers.
panini-nlp (GitHub: akulasairohit/panini-nlp) — Someone has already encoded all 3,996 sūtras as a computable directed graph with a deterministic sandhi engine + GNN layer for ambiguity. MIT licence. This is directly usable for the Pāṇini layer we described — don't rebuild it.
SanskritShala (ACL 2023) — web-based toolkit: word segmentation, morphological tagging, dependency parsing, compound identification, all SOTA. Includes 7 word embedding models trained on Sanskrit. Public API. Use this before Heritage Engine — it may be faster.
Sanskrit Sembank + WordNet integration — IIT Mumbai Sanskrit WordNet maps Sanskrit lemmata to synsets. Combined with DCS Sembank: you can get sense-disambiguated philosophical terms across the whole corpus. This directly addresses the "same word, different traditions" problem in provenance labelling.
Navya-Nyāya formalisation — existing work: Ganeri 2008 "Towards a formal regimentation of the Navya-Nyāya technical language I & II" is the primary reference — it maps NN to property-theoretic FOL. The paper on "Later Nyāya Logic: Computational Aspects" (Springer) describes Conceptual Graphs rendering of NN expressions semi-automatically. This is the intermediate step between Heritage Engine output and Lean type — we were going to build it from scratch but this paper already describes the algorithm.

The document doesn't specify what happens at the Navya-Nyāya → FOL → Lean4 type transition in enough detail. The Ganeri FOL mapping exists. The FOL → Lean4 translation is ~200 lines of Lean that needs writing. That's the one piece with no existing solution — should be flagged explicitly.
Also: no mention of Abhinavagupta's Tantrāloka being available in GRETIL in machine-readable form. It is. gretil.sub.uni-goettingen.de has it. The Shiva Sūtras with Kṣemarāja's Vimarśinī are also there.

You are being asked to review and improve a formal instruction document for a Sanskrit Proof Engine — a system that decomposes philosophical claims from Sanskrit texts into Lean4 proofs or honest boundary findings.
Core goals: maximum terseness, zero hallucination, full scholarly traceability.
Every claim in the system must be traceable to either (a) a Lean4 proof that compiles, (b) a named Sanskrit source with IAST reference, or (c) an explicit OUTSIDE_FORMAL / HOLLOW status. Nothing else.
What the system does:
Takes Sanskrit philosophical claims → decomposes recursively → reaches either proved Lean4 nodes or honest boundaries. The graph that results IS the output. High reuse_count nodes = genuine structural primitives. They emerge, they are not declared.
The Pāṇini principle: Terseness is a design goal inherited from Pāṇini's Aṣṭādhyāyī — ~4,000 sūtras generating all of Classical Sanskrit, each rule minimal, modular, no redundancy. Apply this to: node statements (one claim per node, minimum words), decomposition (fewest children that cover the claim), library checks before any new work (reuse over reinvention). The grammar derivation from Heritage Engine / panini-nlp traces through actual Pāṇinian rule chains — these are provable sub-nodes, not assumed.

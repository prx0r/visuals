## 1. Where the project stands (two halves)

Pāṭala is two coupled systems:

1. **The corpus + translation lab** (in `/root/projects/sanskritree`) — the raw Sanskrit, the T1→T3/C1 translation files, the dossiers, the anchors. This is the *content*.
2. **The hub + API/MCP** (in `/root/projects/patala`) — the bibliography, the passage corpus, the 19-route API, the 12-tool MCP, the docs. This is the *infrastructure* that serves the content.

The goal of the current build: make **#1 automated** (a standardised, audited, versioned pipeline T1→T3.1→C1), and have **#2 consume** its structured output.

## 3. The real output formats (what the pipeline must produce)

The translation files live in `sanskritree/translations/{00_legacy,01_t1_working,02_r1_review,03_t2_alternate,04_r2_adjudication,05_t3_final,06_c1_interpretation,_meta}`.

| Stage | File | What it contains |
|---|---|---|
| **T1** | `01_t1_working/*_pass1.md` | one careful working translation per verse + notes ([G] grammar / [P] parallel / [A] anchor / [R] reconstruction) + `[X]` flags + a required **time-place-context** header (PERIOD/PLACE/GENRE/FRAME) |
| **R1** | `02_r1_review/r1_*.md` | the *prosecutor's review*: re-reads T1 vs the source + anchor; verdicts **RIGHT / ERROR / FORK / OPEN**; quotes the anchor verbatim |
| **T2** | `03_t2_alternate/*` | a fresh translation with a *different strategy* (blind of T1's sentences) — the second voice |
| **R2** | `04_r2_adjudication/r2_*.md` | compares T1-vs-T2, adjudicates, grows the commentary, converges on the reading |
| **T3** | `05_t3_final/t3_*.md` | the resolved final text; OPEN flags carried inline |
| **T3.1** | *(derived from T3 — the reading layer)* | natural-English reading translation, updates in lock-step with T3 |
| **C1** | `06_c1_interpretation/c1_*.md` | plain-English interpretation per verse (independent research; may overturn T3) |

**Example (Śivasūtra 1.1):**
- **T3:** `1.1` — Consciousness is the Self. *(one's own essential nature, per the Vārttika's gloss)*
- **C1:** "You are not a body that happens to be conscious. You are consciousness itself..."

**The audit discipline (from `_meta/PASS_PROTOCOL.md` + `R1_CONTENT_ENGINEERING.md`):**
- A translation choice is justified if it cites [G]/[P]/[A]/[R].
- Corrections are recorded, never silently overwritten.
- `[X]` flags are only resolved with evidence.
- The anchor is diagnostic, not ground truth.
- Status vocabulary: `✓ derived`, `[X] provisional`, `[R] reconstruction`, `[D] divergent-from-anchor`.

## 4. The next big build: the automated translation pipeline

**The goal (user's ask):** a full pipeline producing structured **T1 → T3.1** plus a **C1 commentary** for each text, with a **standardised process** and **data auditing at each level**, so the whole thing can be **automated**.

### The design (build first, wire the API after)
A standalone orchestrator that drives the existing 7-stage pipeline with the model as the translator and the evidence sources (anchors, dossiers, concordance, term ledger) as ground truth. Per text it produces **one structured, versioned record per passage**, carrying:

```
passage_id           tantra:text:{work}:{chapter}.{verse}
source               edition + source_text
T1                   working translation + [X] flags + time-place-context
R1                   verdicts (RIGHT / ERROR / FORK / OPEN) + anchor quotes
T2                   the alternate voice
R2                   the adjudication (T1 vs T2 → resolved reading)
T3                   the final resolved text
T3.1                 the natural-English reading layer (derived, in lock-step)
C1                   the plain-English commentary
audit                the schema-validity + evidence-coverage + term-drift checks
version_lineage      each stage's created_by / derived_from / supersedes
```

### The automation layers
1. **Segment** — stable passage IDs from the source (the segmenters already exist).
2. **Translate (T1)** — the model produces the working translation per the house contract (skill/style/evidence policies already written).
3. **Review (R1)** — an independent "prosecutor" pass re-derives from Sanskrit + checks anchors.
4. **Alternate (T2) + adjudicate (R2)** — a second strategy, then converge.
5. **Finalise (T3) + read (T3.1)** — resolved text + derived reading layer.
6. **Comment (C1)** — plain-English interpretation.
7. **Audit + version** — validate the structured record against the schema; record the lineage.

### Immediate next steps (in order)
- [ ] Build the **orchestrator script** (standalone, model + evidence sources, no API dependency).
- [ ] Define the **passage record schema** (the machine shape all stages write into).
- [ ] Build the **audit checker** (schema validity, evidence coverage, term drift, `[X]` honesty).
- [ ] Run it on **one chapter** end-to-end (Kramasadbhāva paṭala 1 is the seeded proof text) → record as the checkpoint.
- [ ] Then wire the structured output into the API/MCP (the passage + translation endpoints already expect verse-anchored records).

# The Per-Work Stacked Artifact — Spec

*2026-08-10. Consolidates the audit-chain principles already specced across the project
into one concrete layout. Sources: `corpus/targets/canonical_reference_map.md` (the peel
chain), `docs/endgame2.md` (the provenance hierarchy), `docs/ENDGAME_SITE_SPEC.md` (the
five levels of authority + the Reader/Workbook), `docs/foundationalideas.md` (stable IDs,
provenance, versioned layers), `translations/_meta/translation_flow_spec.md` (the 7-stage
flow), and `docs/nextdev.md` (assertions/evidence/review as first-class).*

---

## 1. The principle

Every translated work is a **stacked artifact**: one directory per work, with each
stage of the flow as a floor. Every floor is both **content** and **audit** — it records
what was decided, why, and on what evidence, and it peels backward to the source.

> **The stack IS the audit.** You don't score a translation; you *trace* it. Each
> document is a layer that can be peeled back to a verifiable source (the
> reference-map's "every layer can be peeled backward").

## 2. The layout (one directory per work)

```
translations/{work_id}/
  00_source/            the Sanskrit, edition, manuscript notes, anchor(s) — the ground truth
  01_t1.md              working translation (T1)
  02_r1.md              peer review of T1 (R1) — verdicts + commentary stubs
  03_t2.md              the alternative translation (T2) — actively opposes T1
  04_r2.md              the synthesis (R2) — hard-core / divergence / adjudication / commentary
  05_t3.md              final resolved text (T3)
  06_t3_1.md            the reader's edition (T3.1) — natural English, derived from T3
  07_c1.md              the commentary (C1) — reviews the whole stack + its own research
  AUDIT.md              the machine-readable audit record for this work
```

`work_id` is the stable id (`kramasadbhava`, `kubjikamata`, `sivasutra`, ...). The
same id is used in the passage ids (`tantra:text:{work_id}:{ch}.{verse}`) and the
bibliography (`data/atlas/audited.ts` / `bibliographySeed.ts`).

## 3. What each floor is (and what it audits)

| Floor | File | Content | Audits |
|---|---|---|---|
| Source | `00_source/` | the Sanskrit text + edition + anchor(s) + manuscript notes | the ground truth, immutable |
| T1 | `01_t1.md` | constructive working translation + notes ([G]/[P]/[C]/[S]/[A]/[R]) + [X] flags + time-place-context | whether the Sanskrit was translated faithfully |
| R1 | `02_r1.md` | the adversarial critique (machine pass): maps genuine CRUXES (id/type/assumption/rivals/evidence-needed) + verdicts + commentary stubs | whether T1 can fail; where a materially different reading is defensible |
| T2 | `03_t2.md` | the strongest materially-different defensible rival (SEES T1+R1; difference budget; no manufactured disagreement; CONSTRAINED markers) | whether a serious rival reading changes anything |
| R2 | `04_r2.md` | the adjudication BY DECISION: hard-core (agreement + source-constrained) + per-decision status (CONSTRAINED/PREFERRED/OPEN/RECONSTRUCTED) + expanded commentary | which reading is best and why; the evidence |
| T3 | `05_t3.md` | the current resolved scholarly candidate (not "truth forever" — T3 v2 possible) | the settled reading under this review state |
| T3.1 | `06_t3_1.md` | the reader's edition (natural English) | a defensible reading a non-specialist can read |
| C1 | `07_c1.md` | the full-length commentary — reviews the whole stack, does its own research, and is itself a referenceable document. May CHALLENGE T3 (→ RevisionProposal → T3 v2) but never mutates it | the whole stack; may challenge the translation |
| Audit | `AUDIT.md` | the conformance/tracking record (see §4) | the whole work's validation state — every PASS derived from a check, never hard-coded |

## 4. The audit record (AUDIT.md)

`AUDIT.md` is the machine-readable record of the work's state. It carries the
provenance hierarchy (endgame2) and the FoJin trust-states (ENDGAME_SITE_SPEC) and
is generated by the pipeline's validation layer:

```markdown
# {work} — audit record

## Status
- review_status: T3.1           (the highest completed floor)
- floors: [source, t1, r1, t2, r2, t3, t3_1]     (c1 pending)
- passages_total: N
- passages_valid: N · needs_review: N · invalid: 0

## Provenance hierarchy (highest tier present)
MANUSCRIPT / CRITICAL EDITION / PUBLISHED TRANSLATION / ...
(what evidence tier the work currently rests on)

## Integrity
- duplicate ids: 0
- missing work: 0
- missing source: 0
- dangling references: 0

## Epistemic
- machine output never presented as reviewed: PASS
- [X] flags not laundered: PASS
- T3 has a prior R2: PASS

## Passage manifest
✓  tantra:text:{work}:1.8   [T1 R1 T2 R2 T3 T3.1]   valid
◐  tantra:text:{work}:1.9   [T1]                    needs_review (missing time-place-context)
```

## 5. How the pipeline builds it

The pipeline writes each floor as it runs (T1 → R1 → ... → C1), then regenerates
`AUDIT.md`. A floor is "done" when its document exists and passes the audit. The
stack is the single source of truth for the work; the API/MCP reads it.

## 6. The downstream join (what the stack feeds)

- **T3.1** → the Reader's edition (ENDGAME_SITE_SPEC §3.1) — the site's reading view.
- **C1** → a **referenceable document** — the basis for:
  - essays (essay objects → blog posts → videos in the wider ecosystem)
  - the Master Map / Workbook (ENDGAME_SITE_SPEC §3.2/§3.3)
  - scholarly citation (BibTeX/RIS from the work + C1)
- The **stack as a whole** → the foundation audit for the work, and the provenance
  chain the API/MCP serves.

## 7. Migration

The current corpus is flat (`01_t1_working/`, `02_r1_review/`, ...). The stack
**wraps** it rather than destroying it: the flat files become the raw material, and
the stack is the assembled per-work view. A migration script links existing files to
their floors where they exist (a work with a `p2_*` R1 and a `t3_*` gets those floors
filled; the rest stay pending). No existing file is moved or overwritten.
